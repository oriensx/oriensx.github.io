# Drop 式发布：把一个 zip 变成一条子路径 URL

## 场景：临时页面缺一条能直接打开的 URL

一个团队每天都在产出临时页面：AI 生成的单页 HTML、给客户看的活动稿、演示用的 Vite 应用、需要服务端渲染的小工具。它们都要发给别人看，寿命可能只有几天，数量却不断累积。

现有做法各有代价。发到公有云平台要过外网与账号审批，内部数据不便外传。走正式流水线要建仓库、配流水线、申请域名，为一个演示页做这些不成比例。用 FTP 传到静态目录则依赖人工分配路径，谁传了什么、能不能覆盖，全靠口头约定。

目标因此收缩成一句话：提交一个 zip 或本地目录，得到一条可直接打开的 URL，全程不接触服务器。以 `vercel.com/drop` 为例，产物提交后落在 `https://vercel.com/drop/{owner}/{project}`，主域既有路由继续按原规则工作。

## 整条链路：四次请求，加一条访问路径

把上面这句话展开，服务需要依次回答四个问题：**这个包是什么**、**它占用哪条 URL**、**什么时候算发布完成**、**浏览器怎么找到它**。前三个问题对应四次 HTTP 请求，最后一个问题发生在部署之后的每一次访问。

<DeployPipeline />

网页与命令行共用这一组接口，两边行为一致。下面按这个顺序展开，每一节解决上一节留下的问题。

## 第一次请求：判断这个包是什么

`POST /api/drop/inspect` 解压 zip 或接收 multipart 文件列表，返回建议标题、入口文件、识别出的框架、是否需要服务端构建，以及告警文案。这一步**不写盘**，用户确认路径之前就能看到判断结果，不满意可以换包或改配置。

判断的前提是不执行上传物里的任何代码，因此只读取文件名与 `package.json`。规则按固定顺序匹配，命中首条即停止。

<FrameworkDecision />

顺序本身有含义。入口 HTML 的检查放在最前，已经构建好的产物不必再走一遍构建；Next 的两条规则必须相邻且 `export` 在前，否则声明了静态导出的项目会被误判成需要常驻进程。最后一条兜住只有 `package.json` 的项目，仍然执行构建命令，默认在 `dist/` 下寻找产物。

自动识别覆盖不了全部情况，因此上传根目录的配置文件（例如 `drop.json`）可以覆盖入口文件、构建命令、输出目录与运行时。

这一步同时承担过滤。浏览器选择文件夹时排除 `node_modules`、`.git`、`.next`、`.turbo`、`.cache`；服务端解压时再执行同样的前缀过滤，并拒绝可执行与服务端脚本扩展名（`.php`、`.exe`、`.sh` 等）。超过阈值（例如 1MB）的文件只在临时目录保留磁盘路径，配置与 HTML 这类小文件读入内存，整包不必驻留在服务进程中。

包的类型确定之后，下一个问题是它放在哪条 URL 下。

## 第二次请求：确定它占用哪条路径

`GET /api/drop/check?path=&owner=` 检查目标路径是否空闲，已被占用时返回归属信息，供界面决定能否覆盖。这一步之所以必要，是因为主域上 `/login`、`/admin`、API 前缀都已被正式业务占用，用户自选路径存在盖住现网功能的风险。

发布路径由调用方给出，也可以写在配置文件的 `path` 字段里。两者都为空则拒绝部署。缺省约定是 `/{owner}/{project}`，服务端把用户名与项目名转换成合法路径段。

规范化时统一小写、去掉尾斜杠，限制层级（例如最多四级）与总长度；拒绝 `..` 与空段，避免跳出目标目录；路径段只允许字母、数字、连字符、下划线。第一段落在**保留名单**内则直接报错。保留名单决定这套服务能不能与主域共存，主域上每一个已有前缀都要登记，名单随新业务增加，需要放进发布流程里维护。

归属规则接在校验之后：路径空闲则新建，已存在且未声明覆盖返回 `409`，声明了覆盖但归属人不符返回 `403`。每人站点数量设上限，用内存索引按归属人计数，请求不必每次都查元数据存储。

路径确定之后，才能决定这次发布在一次请求内结束，还是要进入构建队列。

## 第三次与第四次请求：部署与轮询

`POST /api/drop` 按第一次请求的判断结果分成两条路径。

<DeployStateMachine />

已是构建产物时，把文件写入数据目录下对应的站点目录，必要时在网站根目录建立软链，元数据记为 `ready`，更新内存路径索引，返回 `200`。整个过程在一次请求内完成。

需要构建时，`npm install && npm run build` 通常耗时几十秒到几分钟，HTTP 请求不适合同步等待。服务端先写入一条 `building` 记录并立即返回 `202`，把临时目录的所有权移交后台任务。任务在临时目录还原源码，执行 `npm install --include=dev`（TypeScript、PostCSS、Tailwind 等通常在 `devDependencies`，按生产模式安装会缺少编译器），再执行构建命令并设定超时（例如 5 分钟）。校验产物时，输出目录下必须存在入口 HTML；静态导出的 Next 项目还要确认配置中声明了 `output: 'export'`。

构建占用大量 CPU 与磁盘 I/O，与主域服务共享机器时并发必须显式限制，用带缓冲的 channel（或任意计数信号量）把同时执行的构建数控制在个位数。

这条异步路径需要一个状态出口，于是有了第四次请求。`GET /api/drop/:id` 轮询到 `ready` 或 `failed`，构建日志随记录返回，设定上限（例如 64KB）并保留尾部，界面直接读该字段。失败时状态改为 `failed`，错误信息与日志一并保存，并释放该任务已占用的端口与进程名，用户看日志尾部即可定位原因。

四次请求结束后，站点已经存在于磁盘上。剩下的问题是浏览器如何找到它。

## 访问路径：只改静态服务器的兜底分支

站点数量会持续增长，为每一个增加一条 nginx location 无法维护。做法是保留原有的 `try_files` 顺序，只把最后一项改成命名 location，由它反向代理到发布服务。

<RequestRouting />

```nginx
location / {
    root /path/to/site;
    try_files $uri $uri/ @drop_fallback;
}

location @drop_fallback {
    proxy_pass http://127.0.0.1:8101;
    proxy_intercept_errors on;
    error_page 404 = /index.html;
}
```

磁盘上已存在的主域文件仍然优先命中，未命中的请求才进入发布服务。发布服务返回 404 时，`error_page` 把请求交回主域的单页应用入口。

发布服务收到的是完整 URL 路径，需要先还原它属于哪个站点，做法是按**最长前缀**匹配。

<PrefixMatch />

站点根一旦确定，站内相对路径也就确定，页面里的相对资源引用才能解析。由长到短的顺序同时保证了嵌套路径的正确性：`/alice/demo` 与 `/alice` 同时存在时，深层站点优先命中，不会被浅层站点截走。

定位到站点之后按运行时分流。静态站点计算相对路径，目录补 `index.html`，无扩展名时再尝试 `.html`，并用相对路径校验结果确认没有跳出站点根目录。常驻进程站点反向代理到本机端口，保持浏览器看到的原始路径。状态为构建中返回 `503`，构建失败或站点不存在返回 `404`。

这里有一处容易忽略的冲突：管理页面（例如 `/drop`）与列表接口共用同一段路径时，浏览器直接打开会看到一段 JSON。判断依据放在请求头上，`Sec-Fetch-Dest: document` 或 `Accept` 中 `text/html` 优先说明这是浏览器导航，返回 404 让静态服务器把请求交回单页应用；带 `application/json` 的请求继续返回列表数据。

访问计数同样不宜逐请求写库，在内存累加，按固定间隔（例如 30 秒）批量写回浏览量与最近访问时间。

到这里静态站点的完整链路已经闭合。带服务端渲染的项目还差一步：部署完成不等于可以访问。

## 常驻进程站点

服务端渲染与 API 路由的项目需要一个持续运行的进程，因此构建之后还要处理框架配置、端口、进程管理与状态恢复。

配置在构建前注入。Next 需要 `output: 'standalone'` 才会产出自带依赖的服务端产物，要求用户改配置会提高使用门槛，因此由服务端处理：已声明静态导出的项目拒绝按此模式部署；已声明 standalone 的原样使用；其余情况把原配置文件改名备份，再生成包装配置，合并原有配置、`output: 'standalone'` 以及与部署路径一致的 `basePath`。没有配置文件时直接生成一份。

**`basePath` 必须与部署路径一致。** 不一致时页面能打开，静态资源与路由前缀会全部错位。这一项由服务端根据实际部署路径写入，构建日志对不一致给出告警。

构建完成后，从预留区间（例如 2999–9999）分配空闲端口并登记到内存端口表；在站点目录写入运行时元数据（端口、启动脚本、进程名、启动模式）；用进程管理器（PM2 一类）启动进程，进程名与站点 ID 绑定；在限定时间内探测本机端口，探测失败则整次部署判定失败并回收端口。standalone 产物不完整时回退为框架自带的 start 命令，前提是构建输出目录仍然存在。两种启动模式都记在元数据里。

进程会随服务重启而消失，所以启动时要对齐状态：读取元数据存储中运行时为常驻进程、状态为就绪的站点，重新启动进程并把端口登记进内存端口表，避免新站点分配到已被占用的端口。

这条路径有两处限制需要提前说明。常驻进程站点不支持修改路径，端口、`basePath`、进程工作目录三者绑定，改 URL 等于重新部署一次。覆盖发布不保留历史版本，回滚需要重新上传旧产物，版本能力要在服务端引入产物快照。

## 同一条链路交给脚本

拖拽页面适合人工操作。脚本与 Agent 走的是同一组接口，只是换成命令行封装：

```bash
# 安装一次
curl -fsSL https://vercel.com/drop/install.sh | bash

# 在项目目录发布
DROP_OWNER=<owner> drop-deploy.sh --dir .
```

脚本在项目目录打包 zip（排除 `node_modules`、`.git`、`.next`），依次调用 inspect、check、部署接口，需要构建时轮询状态，最后输出可访问的 URL。目标路径已属于同一归属人时要求显式声明覆盖。接口根地址通过环境变量指定，用来切换本地与线上环境。

写操作都要带归属人标识，网页从登录态取，命令行从环境变量或参数取。接口若只校验该字段非空，它只是归属标记，**不构成身份认证**。内部工具可以接受，对外开放前必须换成真实鉴权。

## 边界与容量

链路之外还有几处容量约束。上传上限要在两处对齐：静态服务器的 `client_max_body_size` 与发布服务自身的字节上限。只改后端、不改 nginx 时，用户先收到 413，看不到后端的提示文案。同时关闭请求缓冲、放宽读写超时，大包上传才不会中断。

元数据存储是权威数据源，内存里的路径索引只是查询缓存，服务启动时全量加载。发布服务重启后，静态站点的文件仍在磁盘上，常驻进程站点靠状态对齐恢复。

回看整条链路，复杂度集中在两端：入口处的路径规范与保留名单划定安全边界，出口处的路由兜底决定这套服务能否挂在已有主域上。中间的识别、构建与文件读写按常规实现即可。
